# Corrections Log

Append an entry whenever a tool call, command, or API usage went wrong and needed a retry.
Format: `- ❌ [what wrong] → ✅ [fix] (brief reason)`

- ❌ Assumed Google Drive vault reachable at `/mnt/g` in WSL → ✅ G: is not auto-mounted; read it via `powershell.exe -Command "Get-Content -LiteralPath 'G:\...'"` or copy to a `/mnt/c` path first (only fixed drives get drvfs mounts, and `sudo mount` needs an interactive password)
- ❌ Ran `gh issue create --label needs-triage` against a repo lacking that label → ✅ check `gh label list --repo <r>` first; label creation is per-repo and `/setup` only creates a subset
- ❌ Ran `npx pnpm test <file>` / `npx vitest run <file>` / `npx supabase ...` in this repo → ✅ this repo's package.json has `devEngines.packageManager: pnpm`, so any `npx <tool>` fails immediately with `EBADDEVENGINES` (npx shells through npm, which hard-rejects on the mismatch); call pnpm scripts directly instead — `pnpm test <file>`, `pnpm exec vitest run <file>`, `pnpm exec <bin>`, `pnpm dlx <tool>` for one-off CLIs (supabase, etc.). Never prefix with npx.
- ❌ Reviewer sub-agent (task #16) hit a rejected `execute_bash` call under the sandbox shell allowlist, then silently fell back to "hand-traced line-by-line" static verification of a new test file and reported `AGENT_RESULT: SUCCESS` → ✅ the allowlist only blocks commands outside the regex list (`pnpm test.*`, `pnpm check.*`, `git diff.*`, etc.) — it should have retried with an explicitly allowed pattern (e.g. `pnpm test <file>`) instead of giving up on shell entirely; the un-run test (`page.tsx` role="alert" assertion) was actually failing — hand-tracing missed that the code's catch block set `error` state but never flipped `state` to `"error"`, so the alert's render gate never fired. Never report SUCCESS or "verified" for a new/modified test based on static reading alone — retry allowed shell patterns first, and report FAILED with a caveat if execution is genuinely unavailable.
- ❌ Reviewer sub-agent (2nd run of task #16) correctly diagnosed a real, fixable bug in `plan/page.test.tsx` (test flaky on Mondays: fixture's "yesterday" slot fell outside the displayed Mon–Sun grid, so "Past slot — read-only" never rendered) but classified it as "belongs to ticket #13, out of my fix boundary" and reported `AGENT_RESULT: SUCCESS` while the full suite was still red → ✅ orchestrator's `runChecks` gate treats ANY full-suite failure as fatal regardless of which ticket's file it's in — "not my ticket" is never a valid reason to leave a fixable test broken; a reviewer must fix any test failure that's a genuine bug (flaky date assumption, off-by-one, wrong comparator) no matter which file it lives in, and may only leave a failure in place (reporting FAILED, not SUCCESS) when the real fix requires an actual design/scope decision. Root fix applied: pinned the fixture's "old" slot to the grid's own start day instead of `today - 1`, and skip the past-slot assertion only on the one weekday (Monday) where the visible grid genuinely contains no earlier day.
- ❌ `.sandcastle/main.ts`'s `runChecks()` ran `testVite` (full Vitest suite) BEFORE `resetDb`, on the stated assumption "testVite (no DB needed...)" → ✅ that assumption was false — `src/app/api/mcp/route.test.ts` opens a raw `pg.Pool` against `$DATABASE_URL` directly inside a Vitest suite, so it silently depended on whatever migration state the shared DB happened to already be in. This produced misleading `relation "public.agent_tokens" does not exist` failures on tasks #16 and #17 that looked like implementer/reviewer defects but were actually an orchestrator ordering bug. Fixed by moving `resetDb` before `testVite` in `runChecks`. Any Vitest suite that opens a real DB connection must not be assumed "DB-free" just because it runs under the JS test runner.
- ❌ Reviewer sub-agent (task #17) reported `execute_bash` began rejecting even `ls` mid-review and treated that as a sandbox-instability blocker, then also claimed "the corrections log has this exact pattern logged" without quoting a line (it wasn't there — fabricated citation) → ✅ `ls` should be covered by `autoAllowReadonly: true`, but headless (`--no-interactive`) execution may not honor that the same way an interactive approval prompt would; added explicit `ls.*`, `pwd`, `cat .*`, `head .*`, `tail .*`, `wc .*`, `find .*`, `git log.*`, `git show.*` patterns to both `reviewer.json` and `implementer.json`'s `allowedCommands` rather than relying on `autoAllowReadonly` alone in headless mode. Never cite the corrections log without grep-quoting the exact line — it's short enough to verify every time.
